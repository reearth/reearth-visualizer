# Re:Earth Visualizer Plugin Development Workbench

## Background / Problem Statement

### Current Situation

The Visualizer web app (`web/`) is the editor. It already provides an in-app, browser-based plugin development experience, the **Plugin Playground**, at
`/plugin-playground` (`web/src/services/routing/index.tsx:65`), rendered from `web/src/app/features/PluginPlayground` with a Monaco editor, a preset browser,
zip import/export and shareable URLs. This document does not change the Playground; it introduces a separate, standalone runtime that the CLI can launch for
local plugin development, the **Workbench**.

Facts relevant to that runtime:

1. The Viewer (`web/src/app/features/Visualizer`) is shared by the Editor, Published and Playground, and it does not import Apollo or `services/gql` directly,
   so an entry without GraphQL is technically possible.
2. The `published` entry proves that a standalone, no-Auth/no-GraphQL build works: `web/published.html` -> `web/src/published.tsx` -> `web/src/publishedapp.tsx`
   mounts only Theme + I18n and renders `PublishedPage`. It is produced by the same `vite build` through `rollupOptions.input` (`web/vite.config.ts:70-75`).
3. The app already knows how to load a plugin from a URL: `config().devPluginUrls` is read by the Navbar (`web/src/app/features/Navbar/useDevPlugins.ts`), stored
   in `web/src/services/state/devPlugins.ts`, and preferred over the built plugin URL in `usePluginInstance.ts:211-230`. The Workbench can reuse this mechanism
   for local file loading.
4. Viewer defaults are built per consumer: the Editor from scene settings, Published from `published_data`, and the Playground with its own hardcoded values
   (`web/src/app/features/PluginPlayground/Viewer/hooks.ts:36-59`). The Workbench defines its own single default rather than spreading it across consumers.
5. The plugin manifest schema and pack rules live on the server (`server/pkg/plugin/pluginpack/package.go`, `server/schemas/plugin_manifest.json`), and the
   plugin API version is defined in `web/src/app/features/Visualizer/Crust/Plugins/pluginAPI/constaint.ts:1` (`2.1.0`).
6. Release artifacts are named `reearth-web_<tag>.tar.gz` (`.github/workflows/build_web.yml:157-168`) and embedded into the server image
   (`.github/workflows/build_server.yml:81-91`). The Workbench will follow the same release process as a separate artifact.

### Problem

1. A plugin author cannot run the plugin development loop from the CLI alone. `reearth/cli` is adding `products/visualizer`, which needs a viewer it can build,
   download and serve locally, independently of the main web app, rendering a plugin from the author's working directory.
2. The existing in-app Playground serves a different role (a browser editor) and is not designed to be built, served or versioned on its own. The Workbench is a
   different deliverable for a different audience: the CLI, plugin authors and agents working locally.
3. Consistency must be enforced: the Workbench must use the same Viewer and plugin API as the main application, and record the plugin API version and source
   commit it was built from, so a plugin behaves the same everywhere.

### Why This Matters

Plugin development is an **open, developer-facing surface**: any engineer, and increasingly coding agents, should be able to start from the CLI. The artifact that
the CLI launches must be the same Viewer that runs in production, so that "works locally" implies "works in production".

## Goals

1. Provide a standalone, editor-less Viewer entry, the **Workbench**, built and served independently of the main app, that the CLI can download, cache and launch
   locally to render plugins from the author's working directory. It needs no backend and no user login.
2. Allow the Workbench to render plugins loaded from local files or a URL, and reload on save (the development loop).
3. Reuse the exact shared Viewer (`app/features/Visualizer`) and plugin runtime (Zushi); do not fork or copy the rendering code.
4. Build and release the Workbench separately from the main app, with its own version and release cadence, recording the plugin API version and source commit in
   the artifact manifest.
5. Keep the in-app Playground for its existing browser-editor role. The two coexist long term with distinct positioning.
6. Keep the Workbench's contract with the CLI stable (the release artifact and the plugin manifest schema). The CLI's project operations will use a separate
   thin REST API instead of the internal GraphQL API; that API is designed outside this document.

**Expected Outcome**

- An author runs `reearth vis plugin init`, `plugin dev` and `plugin push` end to end without touching the web app.
- A plugin that works in the Workbench behaves identically in the main application and in production.
- The CLI consumes a pinned Workbench build whose Viewer and plugin API version are known.

## Non-Goals

1. An external, embeddable, pure-frontend viewer for third-party websites. That is a different audience and a separate product decision. This design leaves an
   input-adapter seam so it can be added later, but does not commit to it.
2. Replacing or removing the in-app Playground.
3. The design of the CLI's project-operations API. The CLI will use a new thin REST API rather than the internal GraphQL API directly; that API is tracked
   separately and is out of scope here.
4. The CMS CLI and CMS user-JWT support (tracked separately).
5. Shipping a code editor, file tree or preset browser inside the Workbench.

## Functional Requirements

1. `workbench.html` builds to a self-contained static directory that can be served from an arbitrary base path and local port.
2. The Workbench mounts no Auth, GraphQL, Restful or Router providers.
3. The Workbench resolves plugin sources from inputs (implemented):
   - `?dev-plugin=<url>`: fetch `reearth.yml` and `<extension-id>.js` from a local HTTP server.
4. On plugin file change, the Viewer reloads the affected extensions without a full page reload (SSE-triggered remount). Pending Phase 3.
5. The Workbench defines its own single default viewer configuration (tiles and other basic defaults) inside `app/features/Workbench`. It is not shared with the
   main app for now. Cesium ion is not used as a default resource, so no ion token is required.
6. Each build emits an artifact manifest (`workbench-manifest.json`) containing at least `version`, `pluginApiVersion` and `commit`.
7. The Workbench is released independently of the main app: an operator runs the Workbench release workflow with a version; the workflow creates the tag
   `workbench-v<version>` and publishes `reearth-viz-workbench_<version>.tar.gz` to that release.
8. The CLI's local plugin server sends permissive CORS headers so the Workbench can fetch across local ports.

## Build and Packaging

The Workbench is built by a dedicated Vite config, `vite.workbench.config.ts`, with `base: "./"`, writing to `dist-workbench/`. CI packages that directory into
the release artifact `reearth-viz-workbench_<version>.tar.gz` and publishes it to its own GitHub release tagged `workbench-v<version>` (the tag is created by
the workflow; never the main app's `v<tag>` release). A shared fragment supplies the common `alias`, `define` and `vite-plugin-cesium` settings so that the main
app config and the Workbench config stay in sync.

The build writes `workbench-manifest.json` into `dist-workbench/`, populated from `__APP_VERSION__`, the git commit and `REEATH_PLUGIN_API_VERSION`
(`web/src/app/features/Visualizer/Crust/Plugins/pluginAPI/constaint.ts:1`), so the CLI can verify the Viewer and plugin API version it is running.

This keeps the Workbench:

- Self-contained and independently versioned.
- Servable from any local port or subpath, thanks to relative paths.
- Out of the main app's `dist` and therefore out of the server image (`server/internal/app/web_index.go` rewrites and serves the whole main `dist`).
- Small, because the editor and dashboard code is not reachable from the Workbench entry.

## Design

### Terminology

- **Playground**: the in-app editor experience. Part of the main application, shipped in the main build and the server image.
- **Workbench**: the standalone, editor-less Viewer entry. Built and released separately, launched by the CLI.

### Architecture and Responsibilities

The CLI and the Visualizer are separate repositories with a one-way contract. The CLI owns the developer workflow; the Visualizer owns the runtime artifact and
the plugin manifest schema. The CLI's project operations go through a separate thin REST API, which is out of scope for this document and shown here only for
context.

```
reearth/cli                                  reearth-visualizer (this repo)
┌───────────────────────────────┐            ┌───────────────────────────────────────┐
│ cmd/  command tree / flags    │            │ server/  CLI REST API (out of scope)  │
│ products/visualizer           │◄── contract┤ web/     shared Viewer + Workbench    │
│   project ops (REST, ops only)│            │ release: Workbench + presets + types  │
│   plugin init/validate/pack   │            └───────────────────────────────────────┘
│   workbench download/serve    │
│   plugin dev (watch + SSE)    │
│ sdk/  auth / output / config  │
└───────────────────────────────┘
```

| Responsibility                                      | Owner                  |
| --------------------------------------------------- | ---------------------- |
| Workbench static build and release artifact         | Visualizer (this repo) |
| Shared Viewer and plugin runtime                    | Visualizer (this repo) |
| Thin REST API for the CLI (out of scope here)       | Visualizer server      |
| Plugin manifest schema                              | Visualizer server      |
| Plugin API types package                            | Visualizer (web)       |
| Preset definitions as data                          | Visualizer (web)       |
| Workbench download, cache, serve                    | CLI                    |
| Local plugin dev server, watcher, SSE               | CLI                    |
| `init` / `validate` / `pack` / `push` orchestration | CLI                    |
| Auth, output, config, keyring                       | CLI `sdk/`             |

### Standalone Entry

The entry mirrors the `published` entry. New files:

```
web/workbench.html                 # -> /src/workbench.tsx
web/src/workbench.tsx              # bootstrap: set minimal window.REEARTH_CONFIG + createRoot(#root)
web/src/workbenchapp.tsx           # Theme + I18n only, renders WorkbenchPage
web/src/app/pages/WorkbenchPage/   # page wrapper
web/src/app/features/Workbench/    # editor-less viewer feature
web/vite.workbench.config.ts       # base: "./", outDir: dist-workbench
```

`workbenchapp.tsx` follows `publishedapp.tsx`: it must not import `AuthProvider`, `GqlProvider`, `RestfulProvider` or `AppRoutes`. It should reuse the
`Published` theme and i18n providers (`PublishedAppProvider`, `PublishedProvider`) so several entries share one theme definition; both are lightweight and have
no Apollo or auth dependency.

The Workbench does **not** load the main app config. The shared Viewer only reads optional config fields (`featureCollection`, `customProviders`, `plugins`,
`unsafeBuiltinPlugins`), and none are required for local plugin development. The bootstrap therefore sets a minimal in-memory config
(`window.REEARTH_CONFIG = { plugins: "/plugins" }`) and renders directly; there is no `/reearth_config.json` fetch and no CLI config injection. If a future
deployment needs injected settings, add a small, explicit loader.

`app/features/Workbench` renders the shared `app/features/Visualizer` and resolves plugin sources. It must not import `app/features/PluginPlayground` (which
pulls in Monaco, JSZip and editor state).

### Plugin Loading and Reload

The Workbench reuses the existing dev-plugin plumbing and mirrors the Playground's instance construction. It does not mount GraphQL.

Implemented:

1. Parse `?dev-plugin=<url>` and validate that the host is localhost (`localhost` / `127.0.0.1` / `::1`).
2. Fetch `<url>/reearth.yml` and parse it with `js-yaml` (the same parser as `Navbar/useDevPlugins.ts`).
3. Seed `services/state/devPlugins.ts` with `{ id, url: <url>/<id>.js }[]`, so `usePluginInstance.ts:211-230` resolves each extension's JS from the local server
   instead of `pluginBaseUrl`.
4. Build plugin instances from the manifest, mirroring `PluginPlayground/Code/hook.ts`, and pass them to the shared `Visualizer`:
   - `widget` extensions -> `widgets.alignSystem` (using `widgetLayout.defaultLocation`, default `outer/left/top`);
   - `infoboxBlock` extensions -> `layers[].infobox.blocks` on the default layers;
   - `storyBlock` extensions -> a single-page `story` with `showStoryPanel`.
   Simplifications versus the Playground: no schema-default property injection (`property: {}`), no built-in widgets, no preset or editor UI.

Not yet implemented:

- SSE hot reload (Phase 3): the reload protocol is still an open question and depends on the CLI. Extension JS is loaded once per page load.
- The seeded extension list is read from `reearth.yml` once; adding or removing an extension requires a page reload.
- `?dev-plugin=` renders arbitrary code from a URL; it is restricted to localhost.

CORS is required because the Workbench runs on one local port and the plugin server on another. The CLI's plugin server must return `Access-Control-Allow-Origin`.

The plugin source resolution remains the single path:

```
[Author]
   │  yarn start:workbench  +  local plugin server (CORS)
   ▼
open http://localhost:3000/workbench.html?dev-plugin=http://127.0.0.1:<p>
   │
   ▼
[Workbench (no Auth/GQL/Router)]
   ├─ fetch <p>/reearth.yml (js-yaml)
   ├─ seed dev-plugin extension URLs
   ├─ build widgets / infobox / story instances from the manifest
   └─ usePluginInstance.ts resolves each extension JS from <p>/<id>.js
          │
     Zushi Plugin (QuickJS + surfaces)
```

### Viewer Default Settings

Today several consumers build Viewer props independently:

- Editor: scene settings (`Editor/Visualizer/hooks.ts`).
- Published: `published_data` (`Published/hooks.ts:57-88`).
- Playground: its own defaults (`PluginPlayground/Viewer/hooks.ts:36-59`).

The Workbench defines its own single default `viewerProperty` (tiles and other basic defaults) inside `app/features/Workbench`. This default is intentionally
**not** shared with the main app for now: the Workbench is a development environment and its defaults may differ from the Editor's. Sharing can be revisited
later if the two need to converge. Cesium ion is not used as a default resource, so no ion token is involved; if a plugin or scene references external assets
that need credentials, that is handled by the plugin or scene configuration.

The Workbench defines its default scene locally as `DEFAULT_WORKBENCH_LAYERS` (`web/src/app/features/Workbench/constants.ts`): a visible GeoJSON sample-points
layer. Default tiles are OpenStreetMap. Infobox blocks from the manifest are attached to these layers so the infobox API has something to render against.

### Presets as Data

Presets currently embed `reearth.yml` and JS as template strings in `web/src/app/features/PluginPlayground/Plugins/presets/**`. To let the CLI read the same
preset definitions as the Playground (for `plugin init --preset`), move each preset into a real directory of files plus an index, and include the preset
directory in the release artifact. The preset ids, categories and i18n titles remain a stable contract.

### Plugin API Types

Publish the plugin authoring types from `web/src/app/features/Visualizer/Crust/Plugins/pluginAPI/types/` as a package (for example `@reearth/plugin-api`),
versioned with `REEATH_PLUGIN_API_VERSION` (`2.1.0`). The TS plugin template consumes this package instead of copying types into `src/shared/reearthTypes/`. The
same version must appear in the Workbench artifact manifest.

### CLI Contract

The CLI does not call into the Workbench at runtime except by serving it; the Workbench-side contract with the CLI is the release artifact and the plugin
manifest schema. The CLI's project operations are served by a separate thin REST API, which is out of scope for this document.

1. **API**: out of scope. The decision is a new thin REST API for the CLI rather than the internal GraphQL API; it is designed separately.
2. **Auth**: a shared Re:Earth audience accepted by the server alongside the existing audiences, verified by `reearth-accounts`. Token storage and refresh are
   handled by the CLI `sdk/auth`; products never see token strings (`sdk/core/core.go:HTTPClient`, `sdk/httpx/httpx.go`).
3. **Context resolution**: workspace is `--workspace` -> `.reearth.yaml` -> account default; project is `--project` -> `REEARTH_VISUALIZER_PROJECT` ->
   `visualizer.project` in `.reearth.yaml`, matching the CLI `Factory.ProjectValue` order.
4. **Release artifact**: the CLI downloads `reearth-viz-workbench_<version>.tar.gz` from the `workbench-v<version>` release, verifies checksums, caches it under
   `~/.cache/reearth/workbench/<version>/` (`sdk/config/config.go:CacheDir`) and serves it.
5. **Skill/docs**: the CLI product ships `skills/*.md` so agents can discover the Workbench commands.

**CLI-side gaps to close (recorded here for the contract):**

- `internal/ghrelease` cannot be imported by products (`products` may only import `sdk`, enforced by depguard). Promote an asset-download helper to `sdk/`.
- The sdk has no helper for the new REST API; keep product-specific API calls inside `products/visualizer`.
- The sdk `.reearth.yaml` model is `map[string]map[string]any`; nested values such as `visualizer.plugin.build` require a typed accessor or a flattened key.

### Versioning and Compatibility

The Workbench has its own version and release cadence (tag `workbench-v<version>`), independent of the main app. It shares the Viewer source, so what matters
for compatibility is not the version number but the Viewer and plugin API it was built from.

1. The Workbench version is supplied when the release workflow is run; the workflow creates the tag `workbench-v<version>` at the built commit.
2. A published version is immutable: re-running with a different commit is rejected, and re-running with the same commit only refreshes the assets.
3. Each build records `version`, `pluginApiVersion` and the source `commit` in `workbench-manifest.json`.
4. The CLI resolves a Workbench version (flag / cache / default), surfaces it in `plugin dev` output, and can check `pluginApiVersion` for compatibility with the
   target plugin API.

Release flow:

```
workbench-vX.Y.Z
   │
   └─ yarn build:workbench -> dist-workbench -> release workbench-vX.Y.Z
                                                     │
                                             CLI downloads + caches
```

The main app release (`v*`) is entirely separate and is not affected.

### Design Flow

```
[Author]
   │  reearth vis plugin dev
   ▼
[CLI products/visualizer]
   ├─ resolve workbench version (flag / cache / pinned)
   ├─ download reearth-viz-workbench_<version>.tar.gz from release workbench-v<version> (once), verify, cache
   ├─ serve workbench static dir on :PORT
   ├─ serve plugin dir on :PLUGIN_PORT with CORS + SSE
   └─ open http://127.0.0.1:PORT/?dev-plugin=http://127.0.0.1:PLUGIN_PORT
          │
          ▼
[Workbench (no Auth/GQL/Router)]
   ├─ set minimal window.REEARTH_CONFIG (no config fetch)
   ├─ seed dev-plugin state from ?dev-plugin
   ├─ Visualizer + Zushi load reearth.yml + <id>.js
   └─ on SSE "reload" -> bump render key -> refetch + remount
```

The parts above that belong to the CLI (`reearth vis plugin dev`, download/cache, SSE) are not implemented yet. Today the Workbench can be exercised manually:
run `yarn start:workbench` and a local CORS-enabled plugin server, then open `http://localhost:3000/workbench.html?dev-plugin=<url>`. The Workbench fetches and
parses the manifest, builds widget/infobox/story instances, and the Viewer loads each extension JS from the plugin server.

## Potential Impact

1. **Binary/image size**: the Workbench is released as a separate artifact and is not embedded into the server image, so the server is unaffected. The CLI gains
   a download dependency but not a compile-time one.
2. **Source coupling**: `app/features/Visualizer` remains the single runtime. Any change that assumes app-level providers will break the Workbench; the entry
   should be part of the standard test suite.
3. **Version drift**: if a Workbench is built from a different commit than the app, plugin behavior can diverge. The artifact manifest and same-tag build mitigate
   this.
4. **Preset migration**: moving presets from TS strings to files changes an internal module layout; preset ids and categories must remain stable to avoid breaking
   share URLs and the CLI.

   - **Symptom**: The Workbench mounts no Auth/GraphQL provider and sends no GraphQL requests, but Apollo Client is still present in the
     `dist-workbench/` bundle. The shared `app/features/Visualizer` statically imports editor-only field UI:
     - `app/ui/fields` barrel exports `AssetField` (`useAssetUpload` -> `services/api/asset` -> Apollo), which is pulled in by `useFieldComponent`,
       the builtin StoryPanel block editors (`Camera` / `Layer` / `Link` / `Markdown` / `Text`) and `Infobox/.../PropertyList/ListEditor`.
     - `app/ui/fields/Properties` (`services/api/property` -> Apollo) is imported by `BlockWrapper`.
   - **Impact**: Bundle size only. There are no runtime GraphQL calls because no provider is mounted. The Phase 1 acceptance criterion
     "Workbench bundle excludes editor code" is therefore not fully met.
   - **Resolution (separate task)**: Decouple the Viewer from editor-only UI by lazy-loading / splitting the editor components and removing
     `AssetField` from the `app/ui/fields` barrel. Deferred because it touches shared editor code used by the main app.

## Test Plan

1. **Unit/smoke**: the Workbench's default `viewerProperty` renders the shared Visualizer without Auth or GraphQL providers.
2. **Build**: `yarn build:workbench` emits a self-contained `dist-workbench/` with relative asset paths; serving it from a non-root subpath still loads.
3. **Bundle**: the Workbench bundle contains no editor, dashboard, Monaco or Auth code (checked against the build output), guarding the "no providers" and
   "small bundle" goals.
4. **E2E (Workbench)**:
   - Serve a fixture plugin directory and open `?dev-plugin=<url>`. Verify `reearth.yml` and `<extension-id>.js` load and the plugin renders (widgets / infobox /
     story). Implemented; needs a manual/browser pass.
   - Change a JS file; verify the SSE event triggers a remount and the new code runs, without a full page reload. Pending Phase 3.
5. **Parity**: load the same plugin in the main application and in the Workbench; verify identical rendering and plugin API version.
6. **CLI integration**: `reearth vis plugin dev` downloads (and then reuses) the cached artifact, starts both servers, opens the browser and reloads on save.
   Pending the CLI product and Phase 3.

8. **Packaging**: `reearth vis plugin pack` follows `server/pkg/plugin/pluginpack` (keep `reearth.yml`, `reearth_<lang>.yml` and `*.js`; drop HTML/CSS).

## CI/CD Configuration

### Build and Release Requirements

The Workbench has its own build and release pipeline, fully independent of the main web application release. It is triggered manually (the operator provides
the version) and publishes to its own release, so the main app release is never involved. This section describes the requirements, not the implementation.

#### Workflow Requirements

1. **Trigger Conditions**:
   - Manual trigger only: run the workflow with a version (and optionally a ref). The workflow creates the tag `workbench-v<version>`.

2. **Build Steps**:
   - Node.js LTS with Yarn 4 enabled via `corepack` (matching `build_web.yml`)
   - Run `yarn build:workbench` to produce `dist-workbench/`
   - Extract plugin API version from `constaint.ts`
   - Generate `workbench-manifest.json` with:
     - `version`: from git tag
     - `pluginApiVersion`: from source constant
     - `commit`: from git SHA

3. **Packaging**:
   - Create `reearth-viz-workbench_<version>.tar.gz` from `dist-workbench/` contents
   - Generate SHA256 checksum file
   - Verify archive is under reasonable size (target: <10MB compressed)

4. **Release**:
   - Upload both archive and checksum to the `workbench-v<version>` GitHub release (independent of the main app `v<tag>` release)
   - Do not mark it as the repository's "latest" release
   - Retain build artifacts for 90 days for debugging

5. **Required package.json Script**:

   ```json
   {
     "scripts": {
       "build:workbench": "vite build --config vite.workbench.config.ts && node bin/generate-workbench-manifest.js"
     }
   }
   ```

#### Release Artifact Structure

The build produces:

1. **`reearth-viz-workbench_<version>.tar.gz`** - Main artifact containing:
   - `workbench.html` - Entry point
   - `static/` - Bundled JS, CSS, and other assets
   - `cesium-<version>/` - Cesium runtime assets
   - `workbench-manifest.json` - Metadata file with version, pluginApiVersion, commit
   - All paths relative (`./<path>`), servable from any base path

2. **`reearth-viz-workbench_<version>.tar.gz.sha256`** - Checksum for verification

#### Workflow Strategy

**Recommendation**: Independent workflow (`.github/workflows/build_workbench.yml`)

**Rationale**:

- Keeps workbench build isolated from main web build
- Can be triggered and debugged independently
- Failures don't block main application release
- Clear separation in CI/CD pipeline

**Not Recommended**: Extending existing `build_web.yml`

- Would couple two separate deliverables
- Harder to maintain and iterate

#### Release Flow

1. Run the **Build Workbench** workflow with version `1.0.0` (optionally a ref). The tag `workbench-v1.0.0` is created automatically.
2. The workflow builds and publishes `reearth-viz-workbench_v1.0.0.tar.gz` to release `workbench-v1.0.0`
3. CLI downloads the workbench artifact on first use
4. CLI caches at `~/.cache/reearth/workbench/<version>/`

The main app release (`v*`) is a separate pipeline and is not involved.

#### Verification Requirements

Post-release verification should confirm:

- Artifact downloads successfully from release URL
- SHA256 checksum validates
- Manifest contains correct version, pluginApiVersion, and commit
- Archive extracts cleanly with expected structure
- Can be served locally and loads in browser
- `?dev-plugin=` parameter works with local plugin server

## Rollback Plan

1. Notify the issue in the team channel.
2. On the Visualizer side, stop publishing the Workbench artifact; the main app and server are unaffected.
3. On the CLI side, fall back to a previously cached Workbench version, or disable `plugin dev` behind a flag and instruct users to use the in-app Playground.
4. Fix forward and cut a new tag; no data migration to reverse.
